# Dither 背景

Forge 1.20.1 和 NeoForge 1.21.1 的共享背景目录提供 `dither`。开发者图库中可打开「图像抖动」并在效果设置中调整图案、颜色、适配和动画。这里的“抖动”是 **image dithering（图像网点量化）** 的效果名称，不代表已经测得画面运动抖动。默认示例使用用户提供的 [Unsplash 图片](https://images.unsplash.com/photo-1493246507139-91e8fad9978e?q=80&w=2670&auto=format&fit=crop)，随包保存以支持离线预览。

调用方可通过 `appearance.backgrounds().layer(null)` 使用注册背景；视图移除时关闭 layer。默认效果由 `Dither.Options.DEMO` 定义，主题覆盖可使用现有 appearance 编辑和草稿接口。

需要其他资源图像时，每个视图持有一个 `DitherBackground`，构造时传入资源包中的 `ResourceLocation`，绘制时传入 `Dither.Options`、区域、减少动效设置和当前时间，并在移除时调用 `close()`。绘制、关闭和显式 `invalidate()` 都在渲染线程执行。

## 加载与更新

旧实现第一次 `draw` 同步执行 JPEG 解码、Java 双线性缩放、`getRGB` 拷贝、`Dither.apply`、逐像素 NativeImage 写入及全图上传。改变尺寸/配置和 NOISE 动画会在渲染线程再次运行大部分流程，可能造成明显停顿。

现在：

1. 渲染线程取得资源包中的资源快照；图片流打开、解码、适配、网点计算和 ARGB→ABGR 打包由一个共享后台 worker 完成。worker 不访问 Minecraft 单例或操作 GL。
2. 两端资源初始/重载阶段投递一个不读图、不等待的调度预热任务，提前启动 worker 并初始化 record 比较代码；worker 空闲 30 秒后仍可退出。共享执行器最多一个 worker、16 个排队任务；每个实例最多一个运行/排队任务。新的尺寸/配置替换旧请求，不积累逐帧任务。队列满时下次绘制重试，绝不退回调用线程执行图片处理。
3. 同实例复用解码图像和尺寸/fit 相同的适配像素；静态效果不重复处理。公开的 `Dither.apply`、gridSize、pixelRatio、颜色和 fit 语义不变，没有为性能偷偷降采样。仍保留原来的每维最多 2048 逻辑像素限制。
4. 完成的像素只读交给渲染线程。每次 `draw` 最多写入/上传 **65,536 像素（256 KiB）**，整行条带分批提交。这个预算是每个实例每次 draw 的上限，不是多个实例共享的全局每帧预算。
5. 显示纹理与准备纹理双缓冲，新图全部上传完成后才切换。准备期间保留完整旧帧；首次加载则显示配置的底色（默认透明）。不会先展示半张图或读取未初始化像素。相同尺寸后续动画复用两张纹理。
6. NOISE 动画至少间隔 50ms，且前一帧 CPU 处理与上传完成后才请求下一帧。负载较大时降低动画更新频率，不追赶积压帧，也不会因不断请求新时间而永远丢弃旧结果。

减少动效在已有图像时立即冻结当前完整帧，后台刚准备完的动画帧也不会继续改变可见图像；初次加载和显式配置/尺寸编辑仍允许完成。恢复后不补播暂停期间的帧。高对比度沿用背景层关闭装饰规则。

两种加载器的资源重载 apply 阶段显式使所有活跃 Dither 实例失效，包括 CPU 加载中或条带上传中的实例；旧结果不再发布，下一次绘制取得新资源快照。注册表使用弱引用；关闭会清除请求、CPU 缓存和两张纹理。自定义宿主也可以调用 `invalidate()` 重试失败图片。没有全局无界图片缓存，也不为每个背景创建线程。

## 可复现测量

在仓库根目录使用完整 JDK 17+：

```sh
JAVA_HOME=/path/to/jdk sh scripts/benchmark-dither.sh
# 可选：最后追加另一个本地图片路径
# 单独运行“资源加载阶段预热后”的对照（仅 benchmark 等待 200ms，生产不等待）：
JAVA_HOME=/path/to/jdk sh scripts/benchmark-dither.sh \
  src/main/resources/assets/sh_better_ui/textures/background/dither_demo.jpg warmup
```

脚本编译真实 `Dither` / `DitherImagePipeline`，使用随包 demo，重现旧适配+getRGB+网点+打包路径，并测量异步请求的调用时间与后台准备等待时间。它不是单元测试中的计时断言，不以机器相关阈值判失败。

2026-11-16，一次 Linux 云端 JDK 21.0.13 运行（2670×1780 JPEG，单次冷启动，随后每尺寸三次，数值会受机器负载和 JIT 影响）：

| 工作 | 实测 |
| --- | --- |
| 冷 ImageIO 解码 | 1307ms |
| 旧路径 768×260 CPU | 首次 54.7ms，后两次 7.7–9.2ms |
| 旧路径 1920×1080 CPU | 64.6–92.0ms |
| 旧路径 2048×2048 CPU | 103–138ms |
| 未预热的新请求调用 | 首次 worker/类加载启动 22.7ms；后续 0.061–0.237ms |
| 另一进程预热后首次请求 | 1.39ms；资源加载阶段预热投递本身 9.87ms，不包含解码也不等待 worker |
| 新实例首次后台准备等待 | 约 1.1–1.6 秒，等待期间不在 draw 中解码 |
| 同实例后续后台准备等待 | 约 2.2–35.8ms，随尺寸变化 |
| 分批上传所需 draw 次数 | 768×260：4；1920×1080：32；2048×2048：64 |

**边界：**这些是 CPU 路径与调度测量，不能当作用户机器 FPS、Minecraft 帧时或 GPU 测量。解码/计算总成本没有消失，只是移出渲染线程，并缓存适配结果、限制每次复制/上传量。首次线程/类初始化仍有开销，预热将其尽量移到资源加载阶段，但不保证所有环境下的首帧上限；纹理存储分配（`glTexImage2D`）仍是全尺寸渲染线程操作，真实驱动分配成本尚未测量。大图会较晚完整出现，动画更新会变慢，这是保留分辨率而限制每次提交工作量的取舍。不能宣称所有瞬时卡顿已完全消除。

## 验证

无 Minecraft 依赖的回归测试覆盖 4 种 mode × 4 种 color mode × 4 种 fit 与旧路径逐像素一致、静态缓存、队列拒绝重试、请求合并、关闭中/排队中取消、旧结果丢弃、A→B→A 配置快速回退和上传条带预算。主线程 `NativeImage` / GL 上传和实际资源包重载仍需 Minecraft 游戏内验收。

检查清单：首次打开/关闭重开、快速改变尺寸及选项、NOISE 开关和减少动效切换、图片缺失/解码失败、加载或上传中重载资源包、多个背景并存，以及宿主使用非默认 texture/PBO/pixel-store 状态后的继续绘制。NeoForge 26.x 尚无对应背景层实现。
